# Fabric Lite for Kiro CLI — Architecture and Implementation Plan

**Document:** `planfabric.md`  
**Status:** Implementation-ready architecture plan  
**Target:** Kiro CLI installed on the implementation machine  
**Primary objective:** Token-efficient, programmatic AI problem solving through Kiro CLI  
**Date:** 2026-08-03

---

## 1. Executive Summary

Fabric Lite is a small, host-independent command-line runtime that lets Kiro CLI use AI programmatically.

The user gives Kiro a task. Kiro writes one concise TypeScript program and executes it through `fabric-lite exec`. That program performs deterministic work in code, selects only relevant context, invokes a small number of focused Kiro CLI AI calls, validates their structured outputs, optionally verifies the combined answer, and returns one compact final result to the parent Kiro session.

The architecture deliberately keeps the valuable core idea from the original Pi Fabric:

- one programmable execution boundary;
- branching, loops, parallelism, filtering, and data flow expressed in TypeScript;
- AI used only where semantic judgment is needed;
- structured outputs;
- bounded execution;
- only the final useful result returned to the parent conversation.

It deliberately excludes the expensive or unnecessary parts:

- no mesh;
- no swarm;
- no persistent actors;
- no agent-to-agent messaging;
- no council framework;
- no durable task board;
- no dashboard;
- no daemon in version 1;
- no MCP server as the primary bridge;
- no ACP in version 1;
- no autonomous recursive agent tree.

The default reasoning pipeline is:

```text
User request
    ↓
Parent Kiro creates one Fabric Lite TypeScript program
    ↓
Deterministic context selection and task splitting
    ↓
Optional single planning call
    ↓
Two to five focused Kiro worker calls, optionally parallel
    ↓
Optional single verifier/synthesizer call
    ↓
Schema validation and deterministic post-processing
    ↓
One compact result returned to parent Kiro
```

The central design rule is:

> Use TypeScript for orchestration and AI for judgment.

## 2. Locked Product Decisions

These decisions should be treated as approved unless implementation evidence proves one impossible.

### 2.1 Kiro remains the only AI provider

Every model interaction in Fabric Lite must go through the installed Kiro CLI.

Fabric Lite must not directly call OpenAI, Anthropic, Bedrock, or another model API in version 1.

The AI boundary is an internal adapter:

```ts
interface AiRunner {
  run(request: AiRunRequest): Promise<AiRunResult>;
}
```

The initial implementation is:

```text
KiroHeadlessRunner
```

This allows ACP or another Kiro transport to be added later without changing the public Fabric Lite program API.

### 2.2 Headless Kiro is used in version 1

Version 1 uses one-shot, non-interactive Kiro calls.

Conceptually:

```bash
kiro-cli chat --no-interactive --agent fabric-lite-worker "instruction"
```

The exact flag ordering must be detected from the installed CLI help instead of assumed. Kiro CLI has changed syntax across releases.

Each AI call:

1. starts a fresh Kiro headless invocation;
2. receives one narrow prompt and relevant context;
3. returns one structured response;
4. exits.

No child session persists between calls.

### 2.3 ACP is explicitly deferred

ACP is not required for the first implementation because Fabric Lite does not need:

- persistent child conversations;
- mid-session steering;
- long-running actors;
- session resumption;
- interactive child tool progress;
- shared conversational memory.

ACP may later replace the Kiro headless runner behind the same `AiRunner` interface if process startup overhead is measured to be material.

### 2.4 No swarm, actors, mesh, or agent communication

Workers are independent one-shot calls.

They do not:

- message each other;
- share memory;
- claim tasks;
- negotiate ownership;
- spawn additional agents;
- recursively delegate work.

The parent Fabric Lite TypeScript program owns the complete reasoning graph.

### 2.5 The program is generated by Kiro

The normal user does not write Fabric Lite TypeScript manually.

The parent Kiro custom agent is taught to:

1. determine whether Fabric Lite is useful;
2. generate one small program;
3. run `fabric-lite check`;
4. run `fabric-lite exec`;
5. repair the program once if type checking fails;
6. present the compact result.

### 2.6 Token efficiency is a first-class product requirement

The runtime must enforce call-count, input-size, output-size, concurrency, and time budgets.

It must not depend only on prompt instructions such as “be concise.”

## 3. Goals

Fabric Lite must provide the following benefits over ordinary sequential Kiro use.

### 3.1 Programmatic decomposition

A task can be split in deterministic TypeScript or, only when necessary, by one bounded AI planner call.

Examples:

- one batch per package;
- one batch per directory;
- one batch per five files;
- one task per failing test;
- one task per API endpoint;
- one task per design concern.

### 3.2 Focused parallel reasoning

Independent semantic analyses can run concurrently with a small configured concurrency limit.

The default maximum concurrency is three.

### 3.3 Verification without a large agent system

Important outputs can be rechecked through one verifier call that receives compact worker findings rather than full transcripts.

### 3.4 Context reduction

The runtime selects and projects relevant context before AI calls.

Examples:

- grep relevant symbols;
- read only matching files;
- extract nearby line ranges;
- use Git changed-file lists;
- remove duplicate snippets;
- truncate oversized files;
- pass only worker evidence to the verifier.

### 3.5 Structured outputs

AI results can be required to match a JSON Schema.

Invalid output is rejected or repaired through one bounded retry.

### 3.6 Compact parent context

The parent Kiro session receives only:

- the final result;
- a short error when execution fails;
- optionally a compact execution summary.

It does not receive every child prompt, child transcript, file read, or intermediate transformation.

### 3.7 Predictable cost behavior

Every execution has explicit limits:

- maximum AI calls;
- maximum worker calls;
- maximum concurrency;
- maximum prompt characters;
- maximum result characters;
- maximum execution duration;
- maximum retries.

## 4. Non-Goals

Version 1 must not implement the following.

- Full compatibility with all `pi-fabric` programs.
- Pi extension loading.
- Pi TUI integration.
- Kiro TUI integration.
- Persistent actors.
- ACP child sessions.
- Swarm or council abstractions.
- Agent recursion.
- Long-term memory.
- Cross-session task state.
- Event-sourced mesh state.
- General MCP tool routing.
- Remote execution.
- Multi-user coordination.
- Untrusted-code-grade sandbox security.
- A graphical interface.
- Autonomous code modification without policy controls.
- Direct model-provider SDKs.

These can be reconsidered only after measurements show a real need.

## 5. User Experience

### 5.1 Normal interaction

The user runs Kiro with the Fabric Lite parent agent:

```bash
kiro-cli --agent fabric-lite
```

The user asks:

```text
Audit the authentication flow, identify concrete correctness and security
problems, verify the findings, and suggest the smallest safe fixes.
```

The parent Kiro generates:

```bash
fabric-lite check <<'FABRIC_TS'
const candidates = await fabric.fs.grep({
  query: "auth|token|session|jwt|cookie",
  paths: ["src"],
  maxMatches: 300,
});

const batches = fabric.util.chunk(candidates.files, 4);

const reports = await fabric.ai.parallel({
  tasks: batches.map((files) => ({
    instruction: "Review these files for concrete authentication defects.",
    context: await fabric.fs.readMany({
      paths: files,
      maxCharsPerFile: 16000,
    }),
    outputSchema: schemas.authFindings,
    maxOutputChars: 8000,
  })),
  concurrency: 3,
});

const verified = await fabric.ai.run({
  instruction: `
Verify, deduplicate, and rank these findings.
Reject anything without file-specific evidence.
Return at most ten findings.
`,
  context: reports,
  outputSchema: schemas.verifiedFindings,
  maxOutputChars: 12000,
});

return verified;
FABRIC_TS
```

After type checking succeeds, Kiro runs the same program with `fabric-lite exec`.

The user receives only the compact verified report.

### 5.2 When Fabric Lite should be used

The parent agent should use Fabric Lite when a task has one or more of these characteristics:

- multiple independent files or components;
- repeated semantic analysis;
- comparison across alternatives;
- need for structured verification;
- substantial deterministic filtering;
- likely benefit from two to five focused AI calls;
- a final answer that should be synthesized from evidence.

### 5.3 When Fabric Lite should not be used

The parent agent should use normal Kiro capabilities for:

- a simple factual answer;
- one small file edit;
- one shell command;
- one straightforward search;
- conversational clarification;
- a task that can be solved in one normal Kiro turn more cheaply.

Fabric Lite must not become ceremony around trivial work.

## 8. CLI Contract

### 8.1 Commands

#### `fabric-lite exec`

Execute a checked TypeScript program.

```bash
fabric-lite exec [--file program.ts] [--format json] [--cwd PATH]
```

If `--file` is absent, read from stdin.

Primary usage:

```bash
fabric-lite exec --format json <<'FABRIC_TS'
const files = await fabric.fs.glob({ pattern: "src/**/*.ts" });
return { count: files.length };
FABRIC_TS
```

#### `fabric-lite check`

Type-check a program without executing it.

```bash
fabric-lite check [--file program.ts] [--format json]
```

The parent Kiro should normally call `check` before `exec`.

#### `fabric-lite docs`

Print compact API declarations or detailed documentation.

```bash
fabric-lite docs
fabric-lite docs --compact
fabric-lite docs fs
fabric-lite docs ai.parallel
fabric-lite docs pattern plan-verify
```

The default output must be concise enough to load into a model context.

#### `fabric-lite models`

Query Kiro for available models when supported by the installed CLI.

```bash
fabric-lite models --format json
```

If model enumeration is unavailable, report that clearly and use Kiro’s configured default model.

#### `fabric-lite doctor`

Validate the environment.

```bash
fabric-lite doctor
fabric-lite doctor --format json
```

Checks:

- Node version;
- package integrity;
- `kiro-cli` executable resolution;
- Kiro CLI version;
- authentication status;
- headless invocation support;
- custom-agent availability;
- generated agent validity;
- temporary-directory writability;
- project-root detection;
- one no-tool Kiro smoke call;
- optional `fabric-lite exec` smoke program.

### 8.2 Stream separation

The CLI must obey:

```text
stdout = final machine-readable result only
stderr = progress, diagnostics, warnings, and debug logs
```

No spinner, color code, log prefix, or progress line may leak into stdout when `--format json` is used.

### 8.3 Result envelope

Successful execution:

```json
{
  "version": 1,
  "runId": "run_...",
  "status": "succeeded",
  "value": {},
  "metrics": {
    "elapsedMs": 1000,
    "aiCalls": 3,
    "workerCalls": 2,
    "retries": 0,
    "inputChars": 24000,
    "outputChars": 5000
  }
}
```

Failure:

```json
{
  "version": 1,
  "runId": "run_...",
  "status": "failed",
  "error": {
    "code": "TYPECHECK_FAILED",
    "message": "Program failed type checking",
    "diagnostics": []
  }
}
```

### 8.4 Exit codes

Recommended Fabric Lite exit codes:

```text
0  success
1  runtime or AI execution failure
2  TypeScript check failure
3  configuration or environment failure
4  budget exceeded
5  timeout
6  cancelled
7  invalid structured AI output
```

These are Fabric Lite exit codes, independent of Kiro’s own child-process exit codes.

## 9. Program Model

### 9.1 Program body

Programs are TypeScript function bodies, not complete modules.

Input:

```ts
const files = await fabric.fs.glob({ pattern: "src/**/*.ts" });
return { files };
```

The checker and executor wrap this internally:

```ts
async function __fabricMain(): Promise<unknown> {
  // generated program body
}
```

This preserves the convenient top-level `return` used by the original Fabric style.

### 9.2 Imports

Version 1 generated programs must not use arbitrary imports.

All supported operations are exposed through the `fabric` global.

Reasons:

- smaller prompt surface;
- deterministic capability list;
- easier checking;
- simpler execution isolation;
- no dependency-resolution surprises;
- reduced accidental access to unrestricted Node APIs.

### 9.3 Type declarations

`types/fabric-lite.d.ts` defines the complete model-facing API.

The checker creates a virtual TypeScript project containing:

- the wrapped program;
- `fabric-lite.d.ts`;
- a strict compiler configuration.

Recommended TypeScript settings:

```json
{
  "strict": true,
  "noImplicitAny": true,
  "noUncheckedIndexedAccess": true,
  "exactOptionalPropertyTypes": true,
  "useUnknownInCatchVariables": true,
  "target": "ES2022",
  "module": "NodeNext"
}
```

Diagnostics must include line and column numbers mapped back to the original unwrapped input.

## 10. Minimal Model-Facing API

Keep this API deliberately small.

```ts
declare const fabric: FabricLiteApi;
```

### 10.1 `fabric.fs`

```ts
interface FabricFsApi {
  read(input: {
    path: string;
    maxChars?: number;
    startLine?: number;
    endLine?: number;
  }): Promise<FileReadResult>;

  readMany(input: {
    paths: string[];
    maxFiles?: number;
    maxCharsPerFile?: number;
    maxTotalChars?: number;
  }): Promise<FileReadResult[]>;

  glob(input: {
    pattern: string;
    cwd?: string;
    maxResults?: number;
    ignore?: string[];
  }): Promise<string[]>;

  grep(input: {
    query: string;
    paths?: string[];
    glob?: string;
    maxMatches?: number;
    contextLines?: number;
  }): Promise<GrepResult>;

  write(input: {
    path: string;
    content: string;
  }): Promise<{ path: string; bytesWritten: number }>;

  patch(input: {
    path: string;
    patch: string;
  }): Promise<PatchResult>;

  stat(input: {
    path: string;
  }): Promise<FileStat>;
}
```

Requirements:

- resolve all paths against the configured project root;
- reject path traversal;
- reject symlink escape unless explicitly configured;
- cap file count and character count;
- use UTF-8 text by default;
- return truncation metadata;
- never silently read secrets ignored by policy.

### 10.2 `fabric.git`

```ts
interface FabricGitApi {
  status(): Promise<GitStatusResult>;

  changedFiles(input?: {
    base?: string;
    includeUntracked?: boolean;
  }): Promise<string[]>;

  diff(input?: {
    base?: string;
    paths?: string[];
    maxChars?: number;
  }): Promise<GitDiffResult>;
}
```

These helpers are valuable because changed-file projection is often the cheapest relevant context.

### 10.3 `fabric.shell`

```ts
interface FabricShellApi {
  run(input: {
    command: string;
    timeoutMs?: number;
    maxOutputChars?: number;
    cwd?: string;
  }): Promise<ShellResult>;
}
```

Version 1 shell behavior:

- disabled by default for generated programs;
- enabled by configuration for approved command patterns;
- no interactive commands;
- child process group killed on timeout;
- stdout and stderr captured separately;
- output truncated with metadata;
- working directory contained within project root;
- environment filtered;
- secrets not forwarded by default.

### 10.4 `fabric.ai`

```ts
interface FabricAiApi {
  run<T = unknown>(input: AiRunInput): Promise<AiRunResult<T>>;

  parallel<T = unknown>(input: AiParallelInput): Promise<AiRunResult<T>[]>;

  map<TItem, TResult = unknown>(input: AiMapInput<TItem>): Promise<AiRunResult<TResult>[]>;
}
```

`ai.run`:

```ts
interface AiRunInput {
  instruction: string;
  context?: unknown;
  model?: string;
  role?: "planner" | "worker" | "verifier" | "general";
  outputSchema?: JsonSchema;
  maxInputChars?: number;
  maxOutputChars?: number;
  timeoutMs?: number;
  retryInvalidJson?: boolean;
}
```

`ai.parallel`:

```ts
interface AiParallelInput {
  tasks: AiRunInput[];
  concurrency?: number;
  failFast?: boolean;
}
```

`ai.map` is convenience only:

```ts
interface AiMapInput<TItem> {
  items: TItem[];
  createTask: (item: TItem, index: number) => AiRunInput;
  concurrency?: number;
  maxItems?: number;
}
```

The implementation may internally express `map` as `parallel`.

Do not add a separate swarm abstraction.

### 10.5 `fabric.util`

```ts
interface FabricUtilApi {
  chunk<T>(items: T[], size: number): T[][];
  unique<T>(items: T[]): T[];
  sortBy<T>(items: T[], selector: (item: T) => string | number): T[];
  truncate(text: string, maxChars: number): string;
  compactJson(value: unknown, maxChars: number): string;
}
```

Only include deterministic helpers that repeatedly save generated-code tokens.

## 11. Kiro AI Runner

### 11.1 Runner interface

```ts
interface AiRunner {
  name: string;

  doctor(): Promise<RunnerDoctorResult>;

  listModels?(): Promise<ModelInfo[]>;

  run(request: NormalizedAiRequest): Promise<RawAiRunnerResult>;
}
```

### 11.2 Command discovery

Do not assume a fixed Kiro CLI syntax.

At installation or first run:

1. resolve executable from:
   - explicit config;
   - `KIRO_CLI_PATH`;
   - `command -v kiro-cli`;
   - platform-specific executable lookup;
2. run:
   - `kiro-cli --version`;
   - `kiro-cli --help-all`;
   - `kiro-cli chat --help`;
   - `kiro-cli agent --help`;
   - `kiro-cli acp --help`, for capability recording only;
3. record supported flags in a small cache under:
   - project `.fabric-lite/cache/kiro-capabilities.json`, or
   - OS cache directory;
4. construct commands from discovered capabilities.

The implementation must support the current documented stable headless pattern:

```bash
kiro-cli chat --no-interactive "prompt"
```

and agent selection where supported.

### 11.3 Authentication

`fabric-lite doctor` must run `kiro-cli whoami` when available.

Do not:

- store API keys;
- print credentials;
- copy authentication files;
- commit Kiro credentials.

If the installed Kiro version requires `KIRO_API_KEY` for headless execution, report a clear actionable error without exposing the value.

### 11.4 Worker custom agent

Generate a dedicated Kiro worker agent named `fabric-lite-worker`.

Purpose:

- pure semantic reasoning;
- no child delegation;
- no shell;
- no write;
- no MCP inheritance;
- no unrelated steering or skills;
- concise structured answers.

The exact file format must match the installed Kiro version.

For Kiro CLI v2, generate a compatible JSON profile.

For Kiro CLI v3, prefer a Markdown profile with YAML frontmatter or equivalent JSON, tag-based tools, and unified permissions.

The worker should receive no tools unless a measured use case requires read-only tools. Fabric Lite should normally pass projected context directly.

Worker prompt:

```text
You are a bounded reasoning worker invoked by Fabric Lite.

Solve only the supplied subtask.
Use only the supplied context.
Do not delegate.
Do not discuss process or hidden reasoning.
Do not add introductions or conclusions.
Return exactly the requested structured output.
When evidence is insufficient, say so in the schema rather than guessing.
```

### 11.5 Parent custom agent

Generate a `fabric-lite` parent agent.

It should have:

- shell access sufficient to call `fabric-lite`;
- no subagent tool;
- no inherited MCP servers;
- minimal inherited resources;
- a focused Fabric Lite instruction file.

The permission model must allow only the Fabric Lite executable and harmless discovery commands, where the installed Kiro version supports command-pattern permissions.

Do not grant arbitrary shell access merely for convenience.

Parent prompt:

```text
Use Fabric Lite only when a task benefits from programmatic decomposition,
focused parallel analysis, deterministic filtering, or verification.

For trivial tasks, answer normally.

For Fabric Lite tasks:
1. Inspect `fabric-lite docs --compact` when needed.
2. Generate one concise TypeScript program.
3. Prefer deterministic code for splitting, filtering, parsing, sorting,
   deduplication, and selection.
4. Use AI only for semantic judgment.
5. Use at most one planner call, five worker calls, and one verifier call
   unless the user explicitly requests broader work.
6. Pass only relevant projected context to workers.
7. Require structured output for workers and verification.
8. Run `fabric-lite check` before `fabric-lite exec`.
9. Repair a type-check failure once. Do not enter an unbounded retry loop.
10. Return only the final useful result to the user.
```

### 11.6 Capturing Kiro output

Kiro headless prints the first response to stdout but does not guarantee a native JSON envelope in the documented interface.

Fabric Lite therefore defines its own framing protocol in the worker prompt:

```text
FABRIC_RESULT_BEGIN
<valid JSON only>
FABRIC_RESULT_END
```

The parser:

1. finds the last complete framed block;
2. parses JSON strictly;
3. validates against the requested schema;
4. rejects trailing non-whitespace inside the frame;
5. records unframed text only in debug artifacts;
6. retries once with a compact repair prompt if configured;
7. fails with `INVALID_AI_OUTPUT` after the retry.

The repair retry receives only:

- the invalid output;
- schema validation errors;
- the required schema;
- a request to return corrected JSON.

It must not rerun the semantic task unless necessary.

### 11.7 Kiro process behavior

Each Kiro child process must have:

- explicit timeout;
- bounded stdout and stderr buffers;
- cancellation support;
- process-group termination;
- `NO_COLOR=1`;
- `KIRO_LOG_NO_COLOR=1`;
- a controlled working directory;
- filtered environment;
- unique invocation ID;
- captured exit code.

Kiro exit code zero does not override schema validation. Both must succeed.

## 12. Reasoning Patterns

These are documented templates, not persistent agents.

### 12.1 Deterministic split → parallel workers → verifier

Use when files or items can be partitioned mechanically.

```text
select context in code
    ↓
split into 2–5 bounded batches
    ↓
parallel worker calls
    ↓
deterministic deduplication
    ↓
one verifier call
```

### 12.2 Planner → workers → verifier

Use when semantic understanding is needed to choose work units.

Strict limits:

- one planner call;
- planner returns at most five tasks;
- each task has an objective, scope, expected output, and verification hint;
- tasks must be independent where possible;
- one final verifier call.

### 12.3 Independent comparison

Use when evaluating designs or solutions.

- each worker evaluates the same question from a different explicit criterion;
- workers do not see each other’s answers;
- verifier compares rather than blindly merges;
- final output records disagreements and evidence.

This gives some benefits of a council without implementing a council system.

### 12.4 Extract → validate → synthesize

Use for large repositories or logs.

- deterministic search reduces source material;
- cheap worker calls extract structured facts;
- TypeScript validates and filters;
- one strong synthesis call generates the final answer.

### 12.5 Review → patch → verify

Use cautiously for code changes.

- worker identifies evidence-backed changes;
- TypeScript applies a small patch;
- deterministic tests run;
- verifier reviews diff plus test output;
- final result includes files changed and verification evidence.

No separate coder swarm is required.

## 13. Token-Efficiency Policy

### 13.1 Default budgets

Recommended starting defaults:

```json
{
  "maxAiCalls": 7,
  "maxPlannerCalls": 1,
  "maxWorkerCalls": 5,
  "maxVerifierCalls": 1,
  "maxConcurrency": 3,
  "maxRetriesPerCall": 1,
  "maxPromptCharsPerCall": 30000,
  "maxContextCharsPerCall": 24000,
  "maxOutputCharsPerWorker": 8000,
  "maxOutputCharsVerifier": 16000,
  "maxTotalAiInputChars": 120000,
  "maxTotalAiOutputChars": 40000,
  "executionTimeoutMs": 180000,
  "aiCallTimeoutMs": 90000
}
```

These are character budgets because the documented Kiro headless interface may not expose exact token accounting.

If Kiro later exposes reliable token usage, record actual tokens in addition to character estimates.

### 13.2 Context-selection rules

The generated program should:

- use Git changed files first for change-review tasks;
- grep before reading whole trees;
- read line ranges where possible;
- cap file count;
- cap total characters;
- strip binary files;
- exclude dependency, build, cache, and generated directories;
- remove duplicate snippets;
- preserve file paths and line numbers;
- include truncation metadata.

### 13.3 Prompt rules

Every AI call should contain:

1. one narrow objective;
2. only relevant context;
3. explicit output schema;
4. explicit evidence requirements;
5. an explicit maximum number of findings or items;
6. no request for chain-of-thought;
7. no repeated global project description unless needed.

### 13.4 Model policy

Version 1 should default to Kiro’s configured model.

If the installed Kiro CLI supports model selection:

- use a fast or inexpensive model for planning and extraction;
- use the stronger configured model for final verification;
- do not use the strongest model for every independent file by default.

Model names must not be hard-coded without discovery.

### 13.5 No hidden recursive expansion

An AI worker cannot call Fabric Lite or spawn another Kiro worker.

The runner’s worker agent has no shell or delegation tools.

### 13.6 Verification policy

Verification is not automatic for every trivial call.

Use a verifier when:

- output affects code changes;
- workers disagree;
- findings are security-sensitive;
- the task asks for confidence or correctness;
- multiple worker outputs must be reconciled.

Skip verification for simple extraction where deterministic validation is sufficient.

## 15. Execution Runtime

### 15.1 Version 1 runtime choice

Use a disposable Node child process for the MVP.

Reasons:

- fastest route to a working prototype;
- TypeScript and Node codebase align;
- easy debugging;
- easy process-level timeout and cancellation;
- lets the API stabilize before investing in a stronger sandbox.

Important trust statement:

> The Node MVP is for trusted local model-generated programs. It is not a security boundary for hostile code.

### 15.2 MVP restrictions

Even in the Node MVP:

- do not expose `require` or an import mechanism in the documented API;
- wrap and compile generated bodies;
- execute in a disposable child process;
- pass only normalized config and capability handles;
- filter environment variables;
- enforce project-root path checks in host APIs;
- terminate the whole process group on timeout;
- cap memory where practical;
- cap stdout/stderr;
- disable shell by default;
- log capability calls without recording secrets.

A determined generated program may still reach Node globals depending on implementation. Do not claim otherwise.

### 15.3 Future QuickJS hardening

After the API and usage patterns stabilize, replace or supplement the Node worker with QuickJS.

QuickJS is appropriate when:

- stronger isolation is required;
- programs may be less trusted;
- all effects should cross a JSON host bridge;
- runtime portability matters.

This is a later hardening milestone, not a prerequisite for proving the product.

### 15.4 No daemon

Version 1 starts a fresh execution worker for every `fabric-lite exec`.

A daemon may be considered only if benchmarks show that:

- repeated TypeScript initialization is material;
- repeated Kiro discovery is material;
- model-call pooling is possible and useful.

Do not build a daemon speculatively.

## 16. Error Handling and Retry Policy

### 16.1 Type-check errors

- return mapped diagnostics;
- parent Kiro repairs once;
- no automatic runtime execution after a failed check;
- no more than one parent repair attempt unless user asks.

### 16.2 Kiro child failure

Capture:

- command shape without secrets;
- exit code;
- bounded stderr;
- elapsed time;
- invocation role.

Retry only when failure is classified as transient.

Do not retry:

- authentication errors;
- invalid CLI arguments;
- missing executable;
- budget exhaustion;
- schema-invalid output after one repair;
- explicit policy denial.

### 16.3 Invalid structured output

One repair retry maximum.

The repair prompt should be much smaller than the original semantic prompt.

### 16.4 Partial parallel failure

Default behavior:

- `failFast: false`;
- collect successful results and bounded errors;
- verifier receives successful results plus compact failure summaries;
- final result explicitly records incomplete coverage.

For mutation workflows, default to `failFast: true`.

### 16.5 Budget failure

Budget errors must be explicit and include:

- limit;
- consumed amount;
- operation that would exceed it;
- suggested smaller scope.

The runtime must not silently add calls beyond the budget.

## 18. Security

### 18.1 Threat model

Version 1 protects mainly against accidental overreach and runaway execution.

It does not claim to safely execute hostile arbitrary JavaScript.

### 18.2 Required controls

- project-root path containment;
- symlink escape prevention;
- secret-file deny list;
- shell disabled by default;
- command allow list when enabled;
- no inherited worker tools;
- no worker delegation;
- environment filtering;
- process timeout;
- output limits;
- call budgets;
- audit metadata;
- no persisted credentials;
- no automatic approval of arbitrary parent shell commands.

### 18.3 Parent Kiro permissions

The generated Kiro parent agent must not simply trust all shell commands.

It should allow the Fabric Lite binary and required harmless commands only where Kiro’s installed permission system supports command matching.

If the installed version cannot safely restrict shell commands, document the risk and require user approval for each shell call rather than using `--trust-all-tools`.

### 18.4 Worker Kiro permissions

The worker agent should be no-tool by default.

If read tools are later enabled, they must be read-only and project-scoped.

Never enable worker shell, write, subagent, or broad MCP capabilities in version 1.

- A task can be decomposed deterministically.

### Scope discipline

- No mesh.
- No actors.

- No persistent child sessions.
- No daemon.
- No MCP primary bridge.

## 25. Risks and Mitigations

### Risk: Kiro headless output is not reliably machine-readable

Mitigation:

- explicit result framing;
- strict parser;
- JSON Schema validation;
- one repair call;
- bounded raw output retained only in debug mode.

### Risk: CLI syntax differs by installed version

Mitigation:

- capability discovery;
- parse `--help`;
- adapter-generated command;
- smoke test during install;
- no hard-coded unsupported flags.

### Risk: Kiro headless requires different authentication

Mitigation:

- `whoami`;
- no secret persistence;
- clear doctor output;
- honor installed version behavior;
- support `KIRO_API_KEY` through environment only.

### Risk: Multiple workers consume more tokens than normal Kiro

Mitigation:

- Fabric Lite used only for suitable tasks;
- default two to five workers;
- deterministic splitting;
- input character budgets;
- benchmark against normal Kiro;
- verifier skipped when not useful.

### Risk: Planner creates low-quality decomposition

Mitigation:

- deterministic splitting preferred;
- planner limited to five tasks;
- schema requires explicit scope and expected output;
- verifier checks coverage;
- parent can bypass planner.

### Risk: Child Kiro processes are slow

Mitigation:

- concurrency three;
- use workers only when parallel work adds value;
- benchmark startup overhead;
- consider ACP only after measurement.

### Risk: Node execution is not a security sandbox

Mitigation:

- trusted-local MVP label;
- disposable process;
- capability restrictions;
- path and shell policy;
- QuickJS hardening milestone.

### Risk: Parent agent gains arbitrary shell access

Mitigation:

- version-appropriate Kiro permission rules;
- allow Fabric Lite command patterns only;
- otherwise require user confirmation;
- never use `--trust-all-tools` by default.

## 27. Final Approved Architecture

```text
Kiro is the planner and user-facing agent.

Fabric Lite is a small programmable execution runtime.

Kiro writes one checked TypeScript program.

TypeScript selects context, decomposes work, controls parallelism,
processes data, validates results, and enforces budgets.

A small number of stateless Kiro headless calls perform semantic reasoning.

Workers do not communicate, persist, recurse, or spawn other agents.

An optional verifier rethinks and validates the combined result.

Only one compact structured result returns to the parent Kiro session.

Version 1 has no mesh, actors, swarm, daemon, MCP bridge, or ACP.
```

This architecture should deliver the useful “code mode” behavior of Fabric while remaining small, testable, token-efficient, and native to the requirement that all AI interaction happens through Kiro CLI.
