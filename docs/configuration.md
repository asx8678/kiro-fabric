# Configuration

The Agent reads only `$KIRO_HOME/kiro-fabric/data/fabric/config/config.json`; configured MCP federation is in sibling `mcp.json`. Files must be non-symlink, single-link regular files within size bounds and, where POSIX ownership/mode checks are available, current-user-owned and private. Unknown fields, ambient imports, unsafe stdio/OAuth options, changed identities, and malformed configuration fail closed. Persistent configuration uses `schemaVersion: 1`. A valid legacy unversioned file is validated and migrated in memory without rewriting the user's file; newly generated and explicitly migrated configuration is versioned. Unsupported future versions and invalid legacy values are rejected without mutation.

`KIRO_FABRIC_RUNTIME_ROOT` and `KIRO_FABRIC_DATA_ROOT` are installer-owned launch values. `KIRO_FABRIC_DEBUG=1|0` controls tracing. Do not inject reserved `KIRO_FABRIC_*` variables from untrusted launch contexts.

## Navigator setting support

`repo.settings()` and approved `repo.configure()` return the requested `config`,
layer/revision metadata and `settingSupport`. `repo.status()` also exposes the same
support metadata alongside `requested`. These are separate from Fabric config.

`settingSupport["sync.ackClean"]` always reports `supported:false` and
`effective:false`, with the stored boolean as `requested` and a reason. This
upstream clean-state **UI notification** has no native Kiro implementation; setting
it to true does not deliver model context or enable automatic sync. The requested
value is retained for configuration compatibility. Support metadata is read-only
presentation, not an accepted configuration field, and does not change stored
bytes or revision hashes. Other automatic lifecycle limitations remain explicit
in `repo.status().capabilities`.

`fabric.info().fovea.sessionIsolation` explicitly reports MCP-instance ownership,
unsupported native isolation and no guaranteed reset on native `/clear`. A reused
MCP instance can retain focus, results, session settings and rule trust across
native chats. `automaticQualification` reports `ready:false`, all required native
H01–H12 gates and no qualified native gates; neither guest input nor an environment
flag enables them. This is a limitation report, not a session-isolation fix.

Managed standard/review profiles set `KIRO_FABRIC_FOVEA_CALL_CONTEXT=1`; minimal sets `0` so an inherited opt-in cannot enable hints. With a generation-matched parser this enables a **same-call** visible Navigator suffix after successful observed `local.read`/`readMany`/`write`/`edit` work in that `fabric_exec`. It is not native session routing, prompt/stop delivery, or `--fovea-hook` registration. `fabric.info().fovea.callContext` reports `invocation-local-visible` or `disabled`. Successful current `repo.focus`/`sketch`/`dwell`/`impact`/`augment`/`anchors`/`rules`/`sync` in the same call skip a redundant suffix; `repo.status`/`settings` do not. Failures, uncertain effects, disabled `sync.mode`, a busy analysis engine, and no-tool turns skip it. Automatic collection also requires `approvals.read=allow`; `ask`/`deny` skip without prompting so an approved write cannot become an unapproved repository-wide read. Notices are disposable per invocation (not the 32-entry native-sync outbox). Up to 16 observed files are analyzed (a sampled note is added when more were seen). Collection uses remaining outer time and never extends the original deadline: the worker stays 6s cold / 750ms warm, with a 2s cleanup reserve and 1s admission headroom inside a 9s collection cap. Native `/clear` still does not isolate MCP-owned focus from other chats.

## Privacy compatibility after browser removal

`privacy.mode` remains `"standard"` (default) or `"restricted-web"`. The latter still blocks unmediated shell and MCP paths; removing browser support must not silently relax an existing privacy policy. This is an application policy, not OS/network confinement.

The bundled browser runtime, browser skill pack, operator commands and legacy `web.search`/`web.open` provider have been removed. No browser executable or replacement web provider is required or automatically installed.

Configuration containing a `web` or `browser` section now fails closed with an actionable error, including disabled or empty legacy sections. Remove only those obsolete sections from your private configuration, preserving `privacy`, `approvals` and unrelated settings. The loader does not rewrite files or touch retained browser profiles, consent records or other user data. Programmatic normalization rejects these sections too. Existing restricted policies remain effective after migration.

## Evidence tooling and explicit profiles

Strict checked-TypeScript Code Mode remains the only model tool path. No model switching, subagents, review guidance loading, source scanning, probe execution, or network installation is triggered automatically by these APIs.

- `local.readEvidence({windows,maxChars?,partial?})` returns a compact `KIRO_LOCAL_EVIDENCE/1` string with numbered source and a final `META` JSON footer. Preserve the whole packet. Metadata includes hashes, source offsets, remaining requests, suffixes and failures. The entire JSON-serialized string is budgeted; `complete` covers requested windows, not whole files or model inspection. Arbitrary caller transformations can still discard a packet.

The installer accepts `--guidance standard|review|minimal` (default `standard`) and writes that variant as the `kiro-fabric` profile. Minimal attaches no Fabric skill/steering resources or startup hook; Kiro-global context and user-supplied instructions are outside that guarantee. All modes preserve tool approvals and Code Mode.

`fabric.info().runProvenance` separates hashed launch declarations from server observations. The launcher supplies `KIRO_FABRIC_RUN_DECLARATION` through the profile's explicit environment handoff; it never authorizes effects. Direct launches without this handoff report unknown declarations. Configured resource hashes identify configured references, not evidence of loaded file contents. Runtime version/bundle identity can be observed without reading the repository or spawning Git; actual model routing and guidance delivery remain unknown unless independently evidenced. The explicit `comparison:provenance` CLI captures supplied comparison files. Neither static configuration nor matching guidance bytes proves model comprehension.

## Execution admission and discovery bounds

`executor.memoryLimitBytes` (default 64 MiB) bounds each guest twice. It is passed to QuickJS as the VM object limit, and it also fixes the maximum of that execution's WebAssembly linear memory, rounded up to whole 64 KiB pages and never below the Emscripten floor of **16 MiB**. The second bound is what contains `ArrayBuffer` and typed-array backing stores, which are allocated from the linear memory rather than the QuickJS allocator and are therefore not covered by QuickJS's own accounting. Growth beyond the ceiling fails the allocation with a controlled out-of-memory result instead of growing host memory; it never aborts the process or the caller's execution. Each execution receives its own module and linear memory, so one guest cannot consume another's capacity, and an exhausted VM is discarded with its module rather than reused. A WebAssembly-level fault raised while creating, running or freeing a VM surfaces as an ordinary `runtime_error` result. Because of the floor, an 8 MiB limit still admits a 16 MiB linear memory; effective guest capacity is that ceiling minus the runtime's own small baseline (measured in tens of KiB), so do not read the configured limit as an exact process-RSS budget.

`executor.maxConcurrentExecutions` defaults to **4** (allowed range 1–64). Each execution service admits at most this many requests across compilation, approval waits and guest execution. Excess requests fail immediately with `Fabric execution concurrency limit reached`; there is no hidden waiting queue. Completion, failure and cancellation release the slot. Closing a service rejects new executions, cancels admitted executions, waits for their bounded settlement, then tears down the registry; it closes only its own compiler pool. This is not proof that arbitrary downstream effects stopped after cancellation. Each service retains at most one idle compiler for 30 seconds; the standalone compiler helper has a separate four-worker bound. These are **per-service**, not process-wide or cross-process limits: embedders must also bound service creation.

Configured MCP discovery follows opaque cursors, including empty strings, under one shared discovery/call deadline and the existing server lease. Enumeration is bounded to 100 pages, 1,000 cumulative tools **before** allow/block filtering, 4,096 characters per cursor, and the existing JSON budget. Cycles, malformed pages and exhausted limits fail the operation rather than returning a deceptively complete partial catalog. These are safety ceilings, not measured throughput targets.

### Provider calls versus interactive approvals

All limits below are **per execution**; configuration keys and defaults are unchanged:

- `executor.maxProviderCalls`: **64** total host calls; `executor.maxConcurrentProviderCalls`: **8** simultaneous host calls. The guest semaphore queues excess parallel work; the host independently rejects excess concurrency.
- `executor.maxApprovalRequests`: **16** admitted interactive approval attempts; `executor.maxPendingApprovals`: **2** simultaneous approval waits. Kiro evaluates explicit `allow`/`deny`/`ask` policy for every action. Silent allow and deny decisions consume neither approval counter, even when prompt budget is exhausted. Read risk alone does not grant permission. Provider-owned elicitations share these counters: manual workspace attachment consumes one attempt on both the guest action and the direct `fabric_workspace` tool, so `executor.maxApprovalRequests: 0` opens no attachment dialog on either path.
- An `ask` reserves both approval counters before elicitation begins. Failed admission opens no prompt and consumes neither counter. Once admitted, decline, cancellation, unavailable elicitation, or an exception still consumes the total attempt; the pending slot is released when the attempt and its cleanup settle. Existing deadlines and effect reservations remain in force.
- Registry approvals and nested MCP stdio/OAuth approval stages share these same counters. Each interactive stage consumes one attempt; silent stages do not.

Library approvers may implement `prepareApproval(action, canonicalArgs, signal)` to return an explicit allow/deny decision or an ask plan with a deferred `prompt()`. Preparation must not interact with the user; it must bind the deferred prompt to the exact canonical request and evaluate policy only once. The service reserves quota before invoking that prompt, without calling `approve()` again. Malformed plans fail closed. Existing custom approvers implementing only `approve()` remain compatible and conservatively charge every callback against both approval limits. Direct Kiro `approve()` callers remain supported, but execution-wide quota enforcement belongs to the execution service.

Provider, audit, result, and deadline limits are independent of approval policy. In particular, `executor.maxAuditEntries` defaults to **64** and `executor.maxAuditBytes` to **64,000**; each pending registry call reserves **8,192 bytes plus its initial audit metadata and 2 bytes of framing** before approval. Once the call and reservation cleanup settle, that reservation is replaced by the actual escaped UTF-8 size of the terminal audit entry plus framing. There is therefore **no fixed 31-call limit**: 64 small sequential audited calls can fit the defaults, while concurrent pending calls and larger terminal entries consume more byte capacity. Admission must fit retained terminal entries plus all pending reservations, as well as the independent provider and entry budgets; this change does not raise any defaults or bypass audits.

## Current runtime provider inventory

`createKiroRuntime` reports seven supported provider names: `fabric`, `local`, `repo`, `artifacts`, `mcp`, `memory` and `state`. It mounts those enabled by configuration and verified bindings and marks the rest unavailable. `KiroRuntime.providers()` (guest-visible as `tools.providers()`) reports current availability. `FABRIC_RUNTIME_PROVIDER_INVENTORY` and `FABRIC_RUNTIME_PROVIDER_REQUIREMENTS` describe the supported providers and their requirements **when registered**; they do not grant authority or replace the live `ActionRegistry.requirements()` checks. Existing unavailable-provider fallback remains unchanged: an unmounted `repo` has no registered requirements, but remains unavailable and cannot be invoked. Unknown configuration sections are ignored by programmatic normalization and rejected for file-backed configuration; configuration and guest-visible descriptors cannot override trusted provider requirements. Explicitly false metadata cannot weaken the registry's established built-in fallback.


## State commit and retry semantics

MCP response artifacts, recovery receipts and explicit checkpoints belong to the authenticated host-session epoch, or to the MCP instance in legacy mode—not to its replaceable workspace runtime. The same owner can retrieve them after detach/select/attach or temporary workspace loss, subject to the normal read approval. Knowing or guessing an ID does not authorize a different owner; retired epochs and restarted processes cannot recover these handles. Legacy MCP ownership is not native-chat isolation, `/clear` invalidation or durable session memory. Standalone library runtimes retain their runtime-local stores.

Explicit `artifacts.checkpoint` calls require write approval and use a separate in-memory store bounded by the smaller of configured artifact limits and 16 entries, 100000 characters per entry, 400000 total characters and a 15-minute TTL. At most eight checkpoint reservations are allowed per execution. Checkpoints are not written to the artifact root or durable memory; only opaque IDs are automatically exposed on later failures. They expire, may be evicted, and disappear on owner retirement. Ordinary overflow artifacts retain their configured store policy. The owner's checked Agent artifact limits are captured at first storage use and are not refreshed by workspace replacement; configuration changes apply to a new owner. Final publication checks remove unavailable handles and report unavailable delivery rather than promising lost evidence. Artifact reads budget the escaped JSON envelope; near-cap formatted output falls back to canonical JSON retention with an explicit omission notice rather than rerunning effects.

A deferred workspace mutation reports execution, workspace transition and result delivery separately. Execution must succeed before commit; a later storage failure cannot undo a committed transition. `workspaceTransition.committed` is `null` if a commit call throws without a trustworthy acknowledgement; inspect `fabric.workspace({action:"status"})` in a fresh execution rather than inferring rollback. Transition diagnostics also respect the output budget after JSON escaping. `retryProgram:false` applies even when output is unavailable: never replay an executed program to recover its output.

State publication occurs at atomic rename after private permissions and file sync have succeeded. Ordinary failures before publication remove only the operation-owned temporary file and leave the previous document intact. Artifact write failures likewise try to remove only the identity-checked, operation-owned file. If disposal fails, the exact file identity and failure remain owned; an uncertain descriptor close is also retained and is never blindly retried. Further response-store writes stop rather than accumulating unaccounted files. Owner retirement attempts all owned cleanup and propagates unresolved failures; replacement files, links and repository-containing directories are preserved. Cleanup itself can fail on an unavailable filesystem; such failures are reported, not presented as successful cleanup.

A post-commit cancellation/deadline or lock-removal failure can reject an operation whose data is already visible. When the provider knows publication succeeded, the error reports `State mutation committed at revision N; acknowledgement failed; read state before retrying`. Do not interpret rejection as rollback. A transport interruption can also lose that acknowledgement: use `state.get` and `state.list` with a fresh request to reconcile entry/document revisions and the intended value or deletion before retrying. Use `expectedRevision` for subsequent writes; do not blindly replay uncertain operations. After a failed lock removal, the same provider retains the exact inode/device cleanup responsibility and retries it before another mutation; it will not remove a replacement lock. Persistent filesystem failure or loss of that provider instance can still require operator recovery after the owning process exits. Do not remove another live process's lock.

This is atomic publication and process-restart persistence, not a guarantee against machine power loss or arbitrary network-filesystem behavior. A directory-entry fsync barrier runs after the rename on platforms with a directory sync contract; a failed barrier is reported as committed-but-unconfirmed (`StateCommitAcknowledgementError` with `durability: "unconfirmed"`) — the mutation is visible but may not survive a host crash, so read state before any retry and never replay external effects from the error alone. Platforms without the contract (Windows) report `directoryBarrier: "unconfirmed"` and never claim crash-safe publication; crash-safe publishers such as the continuity rotation journal refuse their intent operations over an unconfirmed barrier. No storage format migration or new transaction API is introduced.

## Clients without roots or elicitation

Fabric requires a verified workspace and form elicitation for effects that need approval. Clients without MCP roots can use the installer-authorized launch context; clients lacking both remain unbound:

- **Automatic direct CLI binding**: the installed profile sets `KIRO_FABRIC_WORKSPACE_SOURCE=launch-cwd`, explicitly authorizing Kiro's per-session MCP launch directory. `kiro-cli --v3 --agent kiro-fabric` works from a project without MCP roots, shell integration, environment exports, or manual attachment. The path is captured once at backend startup and canonicalized; it is never inferred from `PWD`, model input, or a later runtime cwd. Home, Kiro/Fabric storage, unsafe and overly broad paths remain rejected. Client roots take precedence; ambiguity, removal after observation, or transient failure never reactivates the fallback. Without this profile opt-in, library/custom launches remain explicit-only.
- **Explicit launcher handoff**: `"$HOME/.kiro/kiro-fabric/bin/kiro-fabric"` supplies `KIRO_FABRIC_LAUNCH_WORKSPACE`. The profile forwards `${KIRO_FABRIC_LAUNCH_WORKSPACE}` because Kiro filters inherited variables. A valid explicit handoff overrides the launch-directory source; invalid explicit values fail closed. An unset/unexpanded handoff uses the profile-authorized launch directory, if enabled. No project path is stored globally. See [automatic shell setup](installer.md#automatic-shell-setup-kiro-cli---v3).
- **No MCP roots capability**: checked `fabric.workspace({action:"list"})` reports an explicitly-empty client context; the authorized launch project can nevertheless be bound. Without an authorized launch project, use `attach` with an absolute `path` and form elicitation. If neither source nor elicitation is available, workspace-scoped providers remain unavailable. The operator endpoint `fabric_workspace` remains compatible.
- **Default shell execution / no form elicitation**: defaults are `read: "allow"`, `write: "ask"`, `execute: "allow"`, `network: "ask"`. Shell commands run in a verified workspace without an approval UI; direct file edits, durable memory/state writes, and network actions still require confirmation and fail closed if it is unavailable. **Shell commands have host authority and can write files or access the network; separate write/network policies do not restrict shell effects.** Fresh installs and existing configurations that omit `approvals.execute` use the new default after restarting Kiro. Explicit `ask`/`deny` values are preserved, not overwritten by updates. To opt an existing restricted installation into unattended execution, merge `{"schemaVersion":1,"approvals":{"execute":"allow"}}` into private `data/fabric/config/config.json`, preserving unrelated settings; use `"ask"` or `"deny"` instead to restrict execution. Do not bypass an explicit denial through another capability. Workspace validation, configured-tool boundaries, and execution limits remain enforced.
- **Transient failures** are never treated as removal: a failed roots refresh reports a temporarily-unavailable workspace using the last verified root set, and never unbinds silently.

### Advertised elicitation with a missing client UI handler

Capability advertisement alone is not proof that approvals work. In a local Kiro CLI 2.21.2 v3 session on 2026-09-09, the client received Fabric's form request but logged `No handler registered for method: _kiro/mcp/elicitation`; Fabric then failed closed. The normal updater offered no newer client on that date. This observed missing handler is distinct from an explicit user decline; inspect the client logs before diagnosing a generic approval error.

Shell execution now defaults to `execute: "allow"` and does not require this UI handler. This does not repair elicitation: explicit `execute: "ask"`, direct writes and network operations that require confirmation remain blocked when the handler is unavailable. Preserve explicit restrictions, inspect the client logs, and use a supported client for approval-dependent effects; `settle:true` and retries do not grant permission.
The generated agent profile deliberately omits `model`; `--v3` selects Kiro's V3 harness and is not a model name. The inline `mcpServers.fabric.requestTimeout` is 917000 ms: Fabric's 900000 ms maximum guest deadline plus the 10000 ms compiler allowance, 2000 ms outer cancellation grace, and a positive 5000 ms client-response margin. This keeps Kiro's client deadline strictly later than Fabric's own maximum request envelope.

The generated `mcpServers.fabric.waitForReady` is **true**. Kiro V3 connects MCP servers asynchronously and snapshots the model's tools at turn start; without this flag a headless first prompt can run before `fabric_exec` is registered, even with `--require-mcp-startup`. The flag uses Kiro's readiness barrier, not an arbitrary sleep, and does not expand tool visibility or approve nested effects. A disconnected/failed server still cannot execute tools; readiness is not proof of task success. Refresh an existing installation with `pnpm run agent:update` from the source checkout (or the normal release update) and start a new conversation. Do not manually edit the integrity-tracked installed profile. Local CLI 2.21.1 V3 headless verification confirmed a real `fabric_exec` result after enabling this flag; release qualification remains separate.

By default, [Kiro custom agents inherit](https://kiro.dev/docs/custom-agents/configuration-reference/#disabling-default-resource-inheritance) default steering, skills, and `AGENTS.md`. Fabric preserves that Kiro default and its installer does not write Kiro settings. A user who wants only the resources named by custom-agent profiles can explicitly set:

```sh
kiro-cli settings chat.disableInheritingDefaultResources true
```

The setting is global and workspace-overridable. Re-enable inheritance by deleting the explicit setting:

```sh
kiro-cli settings --delete chat.disableInheritingDefaultResources
```

## Complete output, working rules and immutable skills

The model-facing guidance is split across these sources:

| Layer | Canonical source | Delivery and purpose |
| --- | --- | --- |
| Standing prompt | `scripts/agent-profile.mjs` | Standard owns task scope, proportional planning, acceptance, Navigator-first navigation and output. Review adds a short review core; minimal keeps operation/authorization rules without task steering. |
| First-request context | `src/kiro/first-prompt-guidance.ts` | The submit hook reinforces complexity assessment, Code Mode and Navigator entry points once per session where hooks run. |
| Attached skill | `skills/fabric-exec/SKILL.md` | Standard/review execution mechanics, source evidence, fallback and bounded composition. |
| Installation steering | `resources/steering/fabric.md` | Generation, workspace and shell boundaries. |
| Tool description and help | `src/kiro/mcp-server.ts`, `src/kiro/bootstrap-provider.ts`, `skills/fabric-exec/references/` | Compact API entry points plus on-demand API, workflow and review recipes; generated guidance embeds canonical Markdown. |
| Navigator result context | `src/kiro/fovea-context.ts` | Bounded untrusted repository hints after eligible tool work, not another instruction prompt or proof of source inspection. |

Context budgets count configured source text, not model tokens or observed delivery. The standing prompt and first-request block together are capped at 9,600 characters; the attached skill at 8,500, with an 18,000-character combined ceiling. Detailed API, MCP, storage and review material stays in task-loaded help. The skill points to those contracts instead of repeating their tutorials, and tells the agent not to reload guidance already present. Client/system instructions, inherited resources, schemas and conversation history are additional; listing a resource in a profile does not prove its full body entered the model context.

The standing prompt, first-request reminder and tool description explicitly name Code Mode and Navigator. The standing prompt and skill map supported capability namespaces and use `tools.providers()`, targeted `tools.search` and `tools.describe` for availability and schemas instead of injecting the full catalog. Removed browser/web capabilities are not advertised; configured external tools remain subject to their existing authorization boundaries.

Navigator advisory text remains explicitly untrusted and bounded to at most 8,192 characters within the existing output allowance. Successful current navigation in the same call suppresses a redundant suffix. These are per-call limits: retained conversation history can still grow across calls, and a label is not proof of immunity to prompt injection. Static prompt-size and delivery tests cannot certify model attention, reasoning quality or live cost.

The **always-on agent prompt** requires complete, verified results while minimizing redundant instructions, repeated reads, intermediate output and avoidable tool exchanges. Every requested outcome still needs evidence or a specific blocker; productive investigation of unresolved requirements continues, with no arbitrary word target. Explicit user scope, length limits, tool restrictions and output formats remain binding: user tool bans include pure computation, formatting and verification, and override workflow advice. Requested JSON keeps permitted evidence inside its schema, without fences or post-test prose. For JSON-only requests, suppress visible assistant commentary before/between tool calls: Kiro includes it in `finalText`. Recheck the entire final text without calling tools.

Standing guidance includes plain comments, Git history/edit/staging preservation, commitlint, PR templates, noninteractive commands, no disk/home/ancestor scans, reading supplied files, and explicit permission for GitHub comment mutations. It requires reading current file contents before modification and prefers targeted `local.edit` changes over creating a file with `local.write` unless the requested outcome needs a new file. Directory discovery is conditional on unfamiliar paths; already-known relevant paths can be used directly. Detailed review-reply/resolution and file-backed Markdown procedures are in workflow help. `gh api` uses `--input`, not `--body-file`. `local.read` reads UTF-8 text, not images/PDFs; unavailable capabilities are blockers, not permission to guess.

Exact local API/result shapes stay beside the tool. Known paths need no ritual listing/help; unknown layouts require discovery. For permitted tool work, keep known-schema data pipelines in one bounded execution. Parallelize independent reads, sequence dependencies, retain per-effect approvals and stop for missing evidence or model judgment. Never replay effects to repair presentation.

`fabric.help({topic,offset?,limit?})` exposes fixed immutable topics without workspace binding: `overview` for bootstrap; `api` for TypeScript declarations; `skill` for SKILL.md; `guide` for API prose; `recipes` for executable examples; `workflow` for coding/Git/GitHub procedures; `review` for evidence, coverage and falsification. Completion and output rules live in the standing prompt; help supplies task-specific execution details. The default page requests up to 16,000 characters, within the unchanged maximum and configured JSON budget, so the current API and review topics each fit one normal page. Explicit smaller limits remain authoritative. Follow `nextOffset` on required truncated content. Offsets are zero-based UTF-16 characters, not bytes/lines. Pages fit their actual serialized JSON budget. Help accepts no path/URI, reads no file at request time, executes no example and grants no approval.

For source inspection, `local.readMany({windows:[{path,offset?,limit?}],maxChars?})` returns numbered source with hashes, requested-range completion and explicit remaining requests. Its aggregate JSON budget defaults to 32,000 characters; `maxChars` accepts 1,000–40,000. The runtime clamps it to the smaller of `executor.maxNestedResultChars` and 80% of `executor.maxOutputChars`, leaving headroom for formatting and metadata. Other local read/search/shell caps stay at 20,000 or the configured nested limit. Lower `maxChars` when returning other substantial data; combined results or logs can still overflow the visible cap. Request `limit:2000` when the whole relevant file is needed, or smaller explicit ranges for focused evidence. Reuse `totalLines` from substantive reads instead of separate line-count reads. Continue `remaining` verbatim first. `complete` means those requested windows were delivered, not that the files ended. The top-level `unreadTails` contains hash-bound follow-up windows after the last delivered line per file/snapshot, capped at 2,000 lines each. Once `remaining` is empty, pass relevant tails as the next windows. The lists can overlap; do not concatenate them or replay old continuations. Empty tails do not account for omitted prefixes/gaps or unrequested files, and retrieval does not certify model comprehension or whole-repo coverage.

For literal Bash probes, `local.shell({script,interpreter:"bash",args?})` avoids outer-shell expansion and temporary script files; command mode remains supported. Both shell forms retain the same approvals, effect queue, host authority and cleanup behavior.

Code Mode batches evidence; Kiro controls model selection and reasoning effort. To choose explicitly, list available model IDs with `kiro-cli --v3 chat --list-models`, then start `kiro-cli --v3 chat --agent kiro-fabric --model <available-model-id> --effort high` (replace the placeholder). The installed CLI 2.21.2 advertises these flags. Inside a session, `/model` and `/effort high` provide the corresponding controls. Supported effort levels depend on the model, and higher effort uses more tokens. Fabric does not silently change these settings. Keep model and effort identical when comparing Fabric with the default agent. See [Kiro model and effort controls](https://kiro.dev/docs/reference/slash-commands/#model).

`scripts/generate-agent-guidance.mjs` embeds canonical Markdown; `pnpm run guidance:check` detects stale generated source. Bundles include matching strings and Markdown in one verified generation. Skill access therefore does not depend on optional resource activation or external-workspace shell reads. Detailed API recipes remain task-loaded. The startup contract is short and defers durable workflow rules to standing guidance; the generator retains its UTF-8 validation and 100,000-character bound per pageable Markdown resource. Per-call output, provider and deadline limits still apply; use further calls and continuations to complete a larger investigation.

Update normally and start a **new Kiro conversation** to adopt prompt, descriptions and help together. `resources/steering/fabric.md` retains nonduplicated installation boundaries. Never edit integrity-tracked installed files or duplicate global steering. This is **model guidance**, not a hard output cap, no-tools switch, JSON decoder or perfect-success guarantee. Inventory, approvals, timeout/call/output limits and native exclusion are unchanged; normal resource inheritance remains. See [turn contracts](turn-contracts.md) for the client enforcement boundary.


## First-message investigation context

The managed agent adds task preparation instructions to the first nonempty message in each Kiro chat. Start a new chat with `kiro-cli --v3 --agent kiro-fabric` and submit a request such as `fix this bug`, `optimize this path` or `review this project`. Its agent-scoped `UserPromptSubmit` command hook appends the block before the model receives the request; there is no extra model call. Subsequent messages with the same Kiro session ID receive no new copy, including after resume or a Fabric upgrade. A new chat receives its own copy. Trusted workspace and enabled Kiro hooks are required; Fabric does not change workspace trust.

The compact block asks for a private assessment of complexity from uncertainty, dependencies and failure impact, then identifies outcomes, constraints and acceptance checks. Simple tasks remain proportional. The standing prompt supplies the detailed tracing, counterexample and verification requirements; the hook does not repeat that full workflow.

For repository code work it names the Navigator sequence: `repo.focus` or `repo.focusRead` for a known target, `repo.sketch` otherwise, and `repo.impact` before edits or review conclusions. It reinforces source evidence, reuse, refresh after changes and disclosed fallback for unavailable/no-match/incomplete analysis. The standing prompt and skill retain coverage/continuation mechanics and workspace boundaries. Non-code chat and forbidden tools skip navigation. The block preserves scope/output restrictions and ends with the next unresolved check, required verification/builds, acceptance and exact blockers.

The standing prompt retains the durable task and Navigator rules independently of the hook. Headless sessions currently do not fire the submit hook and rely on that standing prompt; resumed sessions do not receive a second block. Minimal mode has no submit hook or Navigator steering. A blocked requirement stays incomplete while independent work continues. The first-turn block reinforces task preparation without embedding the full coding and review recipes.

The large review starter is loaded only through `fabric.help({topic:"review"})`, with paging when truncated. It combines hidden-aware discovery and source packets in one execution without refetching help. Separate source budgets cover guidance, entrypoints, automation, overrides, configuration, templates, checks and implementation; long documentation cannot consume every area's budget. It returns numbered ranges, hashes, exact continuations, deferred paths and individual failures. Large path metadata requests narrower discovery. The first sample is heuristic and capped at three files per area; this is not an investigation or coverage limit. Follow relevant deferred paths, unread ranges and cross-references with further calls until the requested scope is accounted for. Credential-looking paths are deferred from automatic reading; relevant boundaries still require redacted inspection. A successful retrieval does not prove a completed review.

The canonical startup text is `src/kiro/first-prompt-guidance.ts`; the executable review starter lives in `skills/fabric-exec/references/review.md` and is compiled into immutable help. Tests execute that actual recipe against repository fixtures and check that the built hook delivers the complete startup text once per session. Runtime-discovery and verification-batch recipes are also exercised against available/missing executables, ordinary failing checks, successful counterexamples and literal arguments. Reporting has no fixed word target. Component tests check delivery, matching generated resources and instruction contracts; they do not measure reasoning quality, latency, credit consumption or whether Auto chooses a stronger model. The guidance preserves user scope, tool restrictions, prior authorization and requested output; it does not authorize edits during a review alone.

Kiro's Auto router and reasoning settings remain Kiro's responsibility. More detailed task requirements can describe the desired depth, but this hook cannot force Opus, guarantee a stronger model, or hold a model selection for later turns. Injection once also does not mean processing or billing once: Kiro may retain the block in conversation history. No live routing or review-quality improvement is claimed from the hook's component tests.

The command reads Kiro's hook input on stdin (maximum 2 MiB), writes the context to stdout, and stores a private marker in `data/first-prompts/`. Markers use a hash of the session ID and contain only schema and guidance-hash metadata; they do not store prompts, raw session IDs or workspace paths. An atomic exclusive claim prevents concurrent submissions from injecting twice. This is at-most-once delivery: if the hook crashes after claiming the session but before Kiro receives stdout, that chat may miss the block. There is no delivery acknowledgement. Markers are not expired automatically, so resumed chats stay consumed. Removing a marker allows reinjection and is not needed during ordinary updates.

Invalid hook input or unsafe/unavailable state storage produces a generic error, exit code 1 and no instruction block. Kiro controls how hook failures are presented; this hook does not guarantee that submission stops on error. It performs no workspace reads, network calls or model calls. The next session starts using an updated profile after the normal source installation; do not hand-edit integrity-tracked installed files.

## Strict local coding and bootstrap

The profile exposes only `@fabric/fabric_exec`; no configuration selects hybrid mode. A verified root is required for local coding. Unbound/unavailable sessions retain checked `fabric.info()`, `fabric.help()` and `fabric.workspace()` recovery; the backend data directory is never a project fallback. Select/attach/detach must run separately from workspace operations and commit only after successful guest settlement and lease release. Restart existing Kiro conversations after an upgrade to adopt the new profile inventory.

Search uses the `rg` found on the MCP server's `PATH`; the installed profile sets that `PATH` to the directory of the ripgrep selected at install time plus `/usr/bin:/bin`. Startup rejects a missing, group/other-writable or foreign-owned `rg`.

Search keeps a shared 10-second deadline, 2 MiB process-output bounds, at most 10,000 selected files, 2 MiB per text file and 32 MiB aggregate consumed input. A glob narrows the normal ignore/hidden enumeration before the candidate cap; the raw enumeration still has its output bound. All selected aliases are checked. Grep reads/revalidates batches of at most 256 text files/2 MiB and stops after the requested prefix, reporting `truncated:true` when candidates remain unsearched. Narrow the path or glob when work bounds are exceeded; a small result limit is not a promise of constant enumeration work. Local read/search/write/result bounds are documented in the bundled API. Existing `executor.maxNestedResultChars` also bounds typed local results and canonical approval material. Oversized changes are rejected rather than approving an invisible diff suffix.

Pagination defaults to strict unfiltered enumeration/content validation. Explicit `snapshotScope:"query-v1"` with `paginate:true` narrows snapshot hashing to the actual glob-selected candidates (not just matching grep files); `scope.snapshotScope` reports this versioned contract. Selected membership/content/identity drift and changed ignore selection still reject. Unrelated files outside the glob may change without invalidation. Existing cursor identity/single-use/60-second TTL, eight-snapshot cache and work/output bounds remain unchanged; selected nontext/oversized files remain unsupported. Result pages copy only delivered records, never the full cached result. This reduces work for selective globs, not the cost of querying every file.

`mcp.call` accepts per-call `projection:"full"|"text"|"structured"`. Full/omitted preserves compatibility; lean modes select one representation before registry/guest serialization, with empty string/null for a missing form and no implicit conversion. Selection is bound into canonical approval and never forwarded as a remote tool argument. Raw-response safety limits and error handling remain in force. Registry truncation now budgets the complete escaped preview envelope, retaining original result size in audits without re-executing providers. These are per-call options, not new configuration-file keys.

Known-owned initialization/release failures retain exact inode cleanup responsibility. Cleanup is retried before another mutation; an unavailable identity or replacement lock fails explicitly and is never guessed from a pathname. Descriptor close is attempted once: a throwing close can already have released/reused its numeric descriptor.

Within a Code Mode execution, local write/edit/shell calls are serialized FIFO in host-call arrival order before argument preparation, including generic `tools.call`. This prevents parallel shell calls from colliding with each other without guessing whether commands are read-only. Each operation retains separate approval, validation, audit and cleanup. A rejected predecessor stops remaining local effects for that execution; `settle:true` ordinary nonzero shell results may continue. Waiting uses the outer deadline and existing bounded host-call budgets; no queued action starts after cancellation/expiry. Reads/searches remain parallel and are not ordered against writes: await explicit dependencies. Cross-execution registry conflicts and cross-process locks remain fail-fast.

Local write/edit/shell share a private workspace-data mutation lock across cooperating Fabric processes. Locks are fail-fast, never automatically broken as stale: after a crash/cleanup failure an operator must establish that no owner or descendants remain and inspect affected files before removing an abandoned local lock. Preserve memory/state files; never remove another live process's lock. External editors do not participate; snapshots detect ordinary conflicts but Node pathname checks are not race-proof OS isolation.

Approved `/bin/sh` commands run with host OS authority; cwd does not confine filesystem/network access. The environment is allowlisted, not a sandbox. Process groups receive bounded TERM/KILL cleanup, including leftover children after leader exit. Deliberate process-group escape is unsupported; Linux zombie reaping belongs to host init. No background-job management is advertised. Ordinary nonzero exits retain bounded head-and-tail stdout/stderr: `settle:true` returns the result, otherwise the checked guest can inspect `error.result` after narrowing to `Error`. Failed executions project the last ordinary nonzero result as `lastShellFailure`, separately from error messages/audit telemetry; this may precede a later guest failure. Existing overflow artifacts retain the full bounded projection when capacity permits. Denial, timeout, cancellation and uncertain cleanup are never ordinary settled success. Outer tool allowance never grants inner permissions.

## Long-running chat context

Kiro, not Fabric, owns conversation persistence and compaction. Kiro's documented default is automatic compaction as a conversation approaches its compaction threshold; `/compact` requests it immediately. Fabric installation does not change `chat.disableAutoCompaction`. Inspect the effective explicit value with:

```sh
kiro-cli settings chat.disableAutoCompaction --format json
```

`null` means no explicit override. A user who previously disabled automatic compaction can explicitly re-enable it with:

```sh
kiro-cli settings chat.disableAutoCompaction false
```

This setting does not control the Fabric MCP lifecycle. Within one active Kiro CLI process, ordinary turns and compaction must keep the same Fabric MCP PID/instance and the same runtime generation for an unchanged workspace. That invariant remains an authenticated exact-release-SHA qualification gate, not a behavior claimed from component tests alone. Fabric memory/state is global-data-root-backed and workspace-scoped; do not use it as a duplicate conversation transcript. TTL artifacts and in-memory values are intentionally ephemeral.

Memory mutations can fail after their atomic rename/delete has already become visible, including during deadline checks or exact-identity lock cleanup. Such failures explicitly say the mutation **committed** and instruct callers to read the key before retrying. The common bounded acknowledgement (action reference and set/delete/write/edit operation only, shared by memory/state/local mutations) survives an outer cancellation/deadline result; it never includes the memory key, value, or underlying error cause. Errors without that acknowledgement, including pre-publication failures and no-op deletes, do not claim a commit. Cleanup retries retain descriptor/inode identity evidence where available and refuse to remove unidentified, foreign, or replacement locks; unverifiable initialization reports unresolved cleanup rather than deleting by pathname.
